# Day 1 — AI Dockerfile Optimizer: Learnings

## 🎯 What we built

A FastAPI service that takes a Dockerfile and uses Gemini on Vertex AI to provide optimization recommendations and an optimized Dockerfile.

```text
Dockerfile
    ↓
FastAPI
    ↓
Gemini on Vertex AI
    ↓
Structured JSON
    ↓
Pydantic validation
    ↓
API response

The goal was to build a useful developer tool rather than simply ask an LLM a question.

1. Using Gemini through Vertex AI

We learned how the Google GenAI SDK is initialized for Vertex AI:

client = genai.Client(
    vertexai=True,
    project="dev-8fenak",
    location="global",
)

We also learned the difference between:

genai.Client()

and:

genai.Client(vertexai=True, ...)

The first expects Gemini API credentials, while our application uses Vertex AI configuration.

2. Calling an LLM from Python

We used:

response = client.models.generate_content(
    model=model,
    contents=prompt,
)

The basic interaction is:

Prompt → Model → Response

This is the foundation for the AI applications we'll build throughout the 30-day challenge.

3. Passing the correct data to the LLM

We caught an important mistake:

f"{request}"

when what we actually wanted was:

f"{request.dockerfile}"

The data flow is:

HTTP JSON
   ↓
Pydantic object
   ↓
request.dockerfile
   ↓
LLM prompt

A Pydantic request object and the actual value contained within it are not the same thing.

4. An LLM response isn't automatically an API response

Initially we had:

print(response.text)

Printing the response doesn't return it from FastAPI.

We changed the flow to:

return DockerfileAnalysis.model_validate_json(response.text)

The resulting flow is:

Gemini response
      ↓
Parse
      ↓
Validate
      ↓
Return HTTP response
5. Pydantic as a contract

We defined a response model:

class DockerfileAnalysis(BaseModel):
    summary: str
    score: int
    findings: list[Finding]
    optimized_dockerfile: str

Instead of accepting arbitrary LLM output, we define what our application expects.

This is an important distinction:

Asking AI a question is different from building an application around AI.

Pydantic gives our application a contract for the model output.

6. Structured output

We used:

types.GenerateContentConfig(
    response_mime_type="application/json",
    response_schema=DockerfileAnalysis,
)

This tells Gemini that we expect structured JSON rather than free-form prose.

We also verified the actual SDK API rather than assuming how it works.

Our installed SDK was:

google-genai 2.21.0

The actual generate_content() signature was:

generate_content(
    *,
    model,
    contents,
    config: GenerateContentConfig | GenerateContentConfigDict | None = None
)

This taught us the importance of checking the actual SDK contract.

7. Understanding Python typing and Pylance

We encountered an error because:

response.text

is typed as:

str | None

while:

model_validate_json()

requires a definite string, bytes, or bytearray.

We handled this explicitly:

if not response.text:
    raise HTTPException(
        status_code=500,
        detail="Gemini returned an empty response",
    )

Then:

return DockerfileAnalysis.model_validate_json(response.text)
Lesson

Static type checkers often highlight real edge cases rather than simply being annoying.

8. Inspecting libraries instead of guessing

We used Python's inspect module:

inspect.signature(...)

to inspect the SDK.

We also used:

model_json_schema()

to inspect the schema generated by Pydantic.

For example:

python -c "from app.models import DockerfileAnalysis; import json; print(json.dumps(DockerfileAnalysis.model_json_schema(), indent=2))"

This was particularly useful because we discovered that our original schema contained:

"severity": {
  "type": "string"
}

rather than an enum.

That explained why Gemini could return:

"severity": "High"

even though we intended to restrict it to:

high
medium
low
9. Constraining the model output

We improved the Pydantic model using Literal:

from typing import Literal

class Finding(BaseModel):
    severity: Literal["high", "medium", "low"]

    category: Literal[
        "security",
        "image_size",
        "build_cache",
        "reliability",
        "best_practice",
    ]

    issue: str
    recommendation: str

We also limited the number of findings:

findings: list[Finding] = Field(max_length=5)

And limited the summary:

summary: str = Field(max_length=200)
Lesson

Don't just tell an LLM to be concise.

Define constraints in the application's data model.

10. Prompt engineering for useful output

Our first response was extremely verbose because the prompt broadly asked Gemini to identify problems.

We improved the prompt with explicit rules:

- Return at most 5 findings.
- Prioritize the most important issues.
- Each finding must have a one-sentence issue.
- Each recommendation must be one sentence.
- Do not provide explanations outside the required JSON.
- Do not invent problems that cannot be inferred from the Dockerfile.

This changed the output from a long report into a much more useful developer-tool response.

11. LLM output can look correct while being wrong

Gemini generated:

COPY .

when the intended command was:

COPY . .

It also made recommendations that sounded reasonable but weren't necessarily universally correct.

For example, it initially suggested Alpine as a smaller Python base image. Alpine can be useful, but it isn't automatically the best choice for every Python application because native dependencies can behave differently in Alpine's musl environment.

Lesson

LLM output can be plausible, professional-looking, and technically wrong.

Never blindly trust AI-generated infrastructure changes.

12. AI + deterministic validation

This led us toward a stronger architecture:

                 Dockerfile
                     │
                     ▼
          ┌─────────────────────┐
          │ Deterministic Rules │
          └──────────┬──────────┘
                     │
                     ▼
               Gemini / LLM
                     │
                     ▼
             Structured Output
                     │
                     ▼
                Pydantic
                     │
                     ▼
           Dockerfile Validation
                     │
                     ▼
               Final Result

This is much stronger than:

Dockerfile → Gemini

The goal is:

AI suggests → deterministic validation verifies → user gets the result.

This pattern will become increasingly important as the projects start modifying infrastructure.

🧠 Day 1 Mental Model

If only five things are remembered:

1. LLMs are components, not applications
Application
    └── LLM

The LLM is one component inside a larger software system.

2. Give LLMs structured contracts

Use structured output and schemas rather than relying on free-form text.

3. Validate model output

Use Pydantic or other deterministic validation mechanisms.

4. Inspect instead of guessing

Useful tools:

inspect.signature()
model_json_schema()

Understanding the actual library/API behavior is better than guessing from examples.

5. AI-generated infrastructure must be verified

Be especially careful when AI generates:

Terraform
Kubernetes YAML
Dockerfiles
Shell commands
Production configuration
